# Candidate10 Spine Launch/Drain Ledger

Date: 2026-07-26

## Purpose

This milestone exposes the measured execution boundaries around Spine
maintenance without fitting an opaque top-wrapper constant. The counters are
generated by the execution-driven maintenance state machine and record:

- launch (`maintenance_start_cycle`);
- first and last accepted maintenance memory request;
- last completed maintenance memory response;
- maintenance completion (`maintenance_end_cycle`).

The elapsed maintenance interval must decompose exactly as:

```text
maintenance_cycles
  = launch_to_first_memory_issue_cycles
  + memory_active_span_cycles
  + post_memory_drain_cycles
```

A successful formal Spine row must also have equal issued/completed request
counts and empty task/inflight/staged queues. The shared comparison parent gate
rejects a row whose timing or request ledger does not close.

## Scope boundary

These counters describe the simulated accelerator-core execution interval.
They do not add XRT launch latency, U55C shell latency, or a board-level fixed
residual. The existing 4,490-cycle zero-edge RTL lower bound remains the only
direct top-level maintenance control oracle and remains restricted to that
proven empty-batch path.

## Smoke evidence

Workload: `syn_weighted_diamond_v8__weighted_sssp`, Candidate10 normalized
Spine, SST/DRAMSim3 backend, 150 MHz.

| Counter | Value |
| --- | ---: |
| maintenance start/end | 0 / 6,390 |
| first/last request issue | 1 / 6,257 |
| last request completion | 6,389 |
| launch to first issue | 1 cycle |
| memory-active span | 6,388 cycles |
| post-memory drain | 1 cycle |
| issued/completed requests | 505 / 505 |
| ledger closed | true |

The decomposition is `1 + 6,388 + 1 = 6,390`. This workload is almost entirely
inside the memory-active interval; it does not establish that all graph shapes
have negligible launch/drain overhead.
