# E2E Timing Bridge (4a) — simulator ↔ calibrated component models

_Date: 2026-07-20_

## 1. Goal

Unify the two layers of the repo so the **simulator itself** emits per-stage
end-to-end timing (B / D_span / R) + kernel time + a bottleneck label that
**basically matches hardware**, usable to find bottlenecks and guide HLS work —
non-mechanistic (regression-backed) now, mechanizable later.

Before this change:
- `SpineV0Simulator` (mechanistic event-sim) used **Phase-2-era timing** and
  never charged the tiled-convergence replay that dominates real reader time. It
  emitted structural features but a single, un-validated `cycles`.
- The HW-validated component models (Phase 4C B-stage, D-stage tile, Phase 5A
  reader, E2E ledger) lived in a **separate analysis layer**, never wired back.

This is the "4a bridge": no re-fitting of the science, pure wiring + a
sim-vs-HW validation table.

## 2. What was built

- **`spine_cycle_sim/calibration/bridge.py`** — maps a `SpineV0Simulator`
  result's structural features into the calibrated models and assembles the E2E
  ledger. It writes the sim run in the **exact HW evidence CSV shape**
  (`summary.csv` + `tile_schedule.csv`) and reloads it through the *same* loaders
  the hardware analysis uses, so sim and HW go through identical feature
  extraction. `BridgeModels.load()` fits/loads B (`fit_component_model`),
  reader-v2 (`fit_reader_component_model`), D_span (`build_dspan_predictor`) and
  the overhead term (`compute_overhead_model`) once.
- **`SpineV0Simulator(..., e2e_models=...)`** — opt-in. When a `BridgeModels`
  bundle is passed, `run()`'s result gains an `"e2e"` section
  (B/D_span/R/serial/kernel + bottleneck). Default `None` → result unchanged
  (preserves the prior contract). The bridge is imported lazily so the default
  simulator import stays free of the calibration/scripts layer.
- **`scripts/analyze_sim_e2e_bridge.py`** — runs the sim on synthetic workloads
  that have HW evidence, feeds each through the bridge, and compares the
  sim-driven E2E prediction to the measured HW `median_kernel_e2e_ms` per stage.

### Ledger (unchanged, R stays out of the total)

```
serial_pred = B_pred + D_span_pred + overhead_model      (R diagnostic, NOT added)
D_tail      = max(0, D_span - R)
```

## 4. Feasibility check (why this is honest)

The simulator only runs **synthetic** workloads; real Amazon slices live only in
the evidence layer. So the validation runs the sim on synthetic specs that have
HW evidence, using the existing generators (`generate_multi_source_tile_workload`,
`generate_partition_tile_workload`, `generate_striped_source_tile_workload`) to
reproduce the phase5a / phase3c host specs. (The `--star-onepart` edge_stream
axis has no simulator generator and is skipped.)

Step 0 confirmed the sim's tile schedule matches the hardware host exactly: on
**all 29 validated cases the sim's structural features are byte-identical to the
HW rows** (`structural_match = yes`, 29/29). This is expected — the sim's
`build_tile_schedule` is the same tiling algorithm as the host — and it means the
sim-vs-HW E2E error is **pure component-model error**, plus it independently
validates the simulator's structural fidelity.

## 5. Results — sim-driven E2E vs HW `kernel_e2e`

| group | role | cases | struct. match | median serial err % | max serial err % | median B err % | median D_span err % |
|---|---|---|---|---|---|---|---|
| phase3c_full_holdout | dspan_holdout | 12 | 12/12 | **0.78** | 14.87 | 0.12 | 4.38 |
| phase5a_reader_cal | reader_cal | 11 | 11/11 | **6.87** | 25.83 | 0.76 | 11.15 |
| phase5a_reader_holdout | reader_holdout | 6 | 6/6 | **6.55** | 10.31 | 1.47 | 8.65 |

The bigger maintenance-dominant phase3c cases match HW `kernel_e2e` to **<1%
median** (e.g. `p3c_hold_full_s2_w16384` −0.0%, `p3c_hold_partition_full` −0.0%,
`s40_w768` −0.1%). The phase5a reader-microbench cases match at **~6.5–6.9%
median**. Max errors are on tiny cases where a stage is a few thousand cycles and
the percentage is noise-dominated (e.g. `p3c_hold_multipart_s40_sparse` 14.9%,
`r5a_cal` fixed-dominated cases). The real Amazon exact slices are matched by the
*same* models at ~12% serial (see `docs/e2e_component_model_20260720.md`) — those
cannot be sim-run (synthetic-only simulator).

## 6. What it's for

Run the simulator on a workload → get a per-stage E2E ledger + bottleneck +
what-ifs, matching HW, to guide HLS work:
- `bottleneck_pred` ∈ {maintenance_dominant, reader_dominant, compute_tail_dominant, balanced}.
- what-if speedups: `halve_b_repeated_scans`, `halve_b_level_write_path`,
  `halve_reader_time`, `ideal_bd_overlap` (reused from the E2E layer).
- On these synthetic shapes most cases are maintenance-dominant; the real
  Amazon slices are reader-dominant (active-record replay), per Phase 5A.

## 7. Limitations (honest)

- **Synthetic-only simulator.** Real Amazon slices are matched via the shared
  models, not by running the sim on them (no real-graph loader).
- **Non-mechanistic.** Timing is regression-backed: replay non-linearity and the
  fallback sweep are still folded into coefficients (Gaps 1/2 open). This is the
  4a bridge — the step that lets 4b mechanize one term at a time (each replaced
  mechanism can be checked against this bridge and against HW).
- **Tiny-case noise.** Cases where a stage is a few thousand cycles show large
  percentage error; medians are the meaningful metric and tiny cases are the max
  outliers.
- **edge_stream axis skipped** (`--star-onepart` has no simulator generator).

## 8. Next (per the Gap analysis)

1. **Gap 1 — replay non-linearity**: charge D-stage replay by actual per-(tile,
   source) edge gather + HBM access instead of the flat coefficient; unblocks the
   measured 4.24 cyc/word fallback sweep. First mechanization step, verifiable
   against this bridge.
2. **Gap 2 — HBM realism** (outstanding requests / bank contention / row-buffer
   reuse), which the redundant replay reads are sensitive to.
3. Add a real-graph loader so the simulator can run the Amazon slices directly
   (removes the "synthetic-only" caveat).
